## 1. 現状（2026-10-22 に読んで確認した事実）

### 1.1 すでにあるもの

- 入力から生成までの流れ: テーマ投稿フォーム（`apps/web/components/themes/ThemeRequestForm.tsx`）→ Worker（`apps/api/src/routes/themes.ts`）→ `theme-on-demand.yml` → 5 秒ごとの確認 → 完成したら系譜の木へ移動（上限 12 分）。入力は分野名（テーマ文字列）で、今のまま使う
- 生成器: `apps/pipeline/src/lineage/theme/`。**新しい契約（`relation`・`confidence`・構造化 provenance・`seed_paper_id`・`schema_version`）で出力し、`validateLineageArtifact` で検証済み**
- ビューアは 3 系統: テーマ家系図（`components/themes/LineageTree.tsx`、1,203 行）、一論文の Focus View（`components/lineage/focus/`、監査済みの根拠表示つき）、学会別グラフ（`components/lineage/graph/`）

### 1.2 公開できる系譜が 0 件の理由

- 公開中の 3 テーマ（flash-attention、mixture-of-experts、vision-transformer）は**旧 Python 版が作った旧形式**（`schema_version` なし、edge は `rel`/`conf`、provenance は文字列、`seed_paper_id` なし）。そのため `artifact_contract_v1` と `edge_semantics_complete` が落ちる。**生成器のコードの問題ではなく、再生成していないことが原因**
- 人手で「テーマに合っている」と確認した記録（golden fixture、`paperpilot/data/lineage-audit-fixtures-v1.json`）が全 collection で空。これが無いと `golden_fixture` が通らない
- 学会別 10 件と deep 14 件は、空のデータ・孤立ノード・catalog との不整合も抱えており、後回しにする
- 判定は fail closed のまま変えない（緩めない）

### 1.3 生成が遅い理由（コードからの見積もり。実測はまだ）

- 全体は 8〜15 分と推測。ジョブ内の外部 API 呼び出しが直列、リリース用 workflow が Python のフルテストまで走らせる、ブラウザが完成に気づくのはサイト公開（deploy）の後、の 3 点が大きいと見ている
- 進捗表示（`ThemeRequestForm.tsx` の疑似ステップ）は経過時間で決めており、実際のジョブの状況と連動していない。status API は休眠中
- **訂正**: 当初「全ノードで Semantic Scholar の 3.5 秒待ちが出て数分かかる」と見積もったが、その待ちは Semantic Scholar 経由のときだけ。主な取得元の OpenAlex には無いため、過大かもしれない。**先に実行履歴で実測する**

### 1.4 ビューアの粗い点（影響の大きい順）

1. 大きなグラフでズームと全体表示（fit）が無い
2. テーマ家系図にスマホ向けの設定が無い
3. 選んだノードが URL に出ず、共有できない
4. 根拠（evidence）の一覧は Focus View にしか無く、他の 2 つから行く道が弱い
5. loading / error の文言と見た目が 3 系統で不統一
6. キーボード操作（矢印でノード間を移動）が無い
7. `LineageTree` 本体の描画とキー操作のテストが無い（レイアウトと URL 状態は純関数テストのみ）

## 2. 設計

### 2.1 公開できる系譜を出す（④）

1. 生成器は直さない。3 テーマを**新しい生成器で再生成**する（外部 API と LLM キーを使うので、実行前にユーザー承認）
2. 孤立ノードは edge でつなぐか刈り込む。その規則は生成器の側でテスト付きで決める
3. golden fixture は人手の確認が要る。候補（focus 全件と 20 件以下のサンプル、理由つき）を Claude が出し、**ユーザーが `on_topic` を確認する**。自動で埋めない（fail closed の意味が無くなるため）
4. 再生成のたびに artifact の `input_sha256` が変わるので、fixture の sha も更新する手順を CLI にする
5. quality manifest を再生成して、通過件数を確認する

### 2.2 オンデマンドで作った系譜の扱い（判断待ち）

オンデマンドの結果は、人の確認記録が付く前に見たい。ただし確認記録が無い系譜は公開基準を満たさない。案は 2 つ。

- (a) 推奨: 自動チェックだけを通った結果を「**人の確認なし**」のラベルつきで、監査済みとは別枠に出す。監査済みの表示とは混ぜない
- (b) 公開しない: ユーザーが確認して通ったものだけを出す。入力してもすぐには見られない

(a) は fail closed の方針の例外になるため、ユーザーの決定が要る。決まるまで実装しない。

### 2.3 生成を速くする（③）

効果が大きい順:

1. **実測**: 直近の Actions 実行履歴で各ステップの時間を測る（読むだけ）。以降の優先順位はこれで決める
2. 引用元取得の並列化（実装済み、`8e165bc4`）。OpenAlex の ID だけ最大 4 件を同時に取り、Semantic Scholar は直列のまま。出力の順序は変えない
3. シードごとの references・citations 取得と LLM 分類の並列化（Groq の RPM 内で）
4. LLM 分類キャッシュを `actions/cache` で復元する（CI は毎回まっさらでヒットしていないと推測）
5. オンデマンドでは、リリース側の Python の pytest・lint を省き、軽い検証だけにする。**検証が弱くなるため、レビューの対象にする**
6. 結果を、サイトの公開を待たずに画面へ返す（Worker/KV か raw ファイル経由）。体感は最も良くなるが、実装が大きく、安全面の設計が別に要る。まず 1〜5 の結果を見て判断する

### 2.4 待ち時間の体験（①）

- 進捗を、疑似ステップではなく**実際のジョブの状況**で出す。方法は、Worker の status API を休眠から戻すか、公開済みの小さな進捗ファイルを読むか。無料枠への影響（40 の §5）を見て決める
- 失敗時に、原因の分類・再試行の案内・Issue への導線を出す
- 12 分の上限は、実測後に見直す

### 2.5 ビューアの見た目と操作（②）

小さい順に進める。CSP（インラインのスクリプト・スタイル禁止）を守り、SVG 属性と CSS module で実現する。

- S: スマホ向けの @media と余白、fit ボタン、選択ノードを URL（`?focus=`）に出す、loading / error の文言を共通化
- M: SVG の viewBox によるズームと移動を共通の hook にする（+/- ボタン、`0` で fit、ホイールは Ctrl 併用時のみ）。凡例・関係フィルタ・検索を共通部品にする。ノード詳細に根拠の要約を出し、Focus View へ行く導線をつける。矢印キーでノード間を移動する
- L（別途判断）: テーマ家系図と学会別グラフの描画・レイアウト・型を 1 つにまとめる。大きなグラフ向けのクラスタ折りたたみ。安全の契約（fail closed、検証済みの release だけを表示）は保つ
- すべてに、描画とキー操作のコンポーネントテストを足す

## 3. 実装の進め方

- 順序: 2.3 の実測 → 2.5 の S → 2.4 → 2.5 の M → 2.3 の 3〜5 → 2.1（再生成と確認記録。承認後）→ 2.2（判断後）
- 各ステップで、実装 → 別のエージェントによるレビュー → 修正 → 機械的な確認、を回し、重大・中程度の指摘が 0 になってから次へ進む
- モデル（ユーザー指示 2026-10-22、`~/.claude/CLAUDE.md`）: 実装は Sonnet、レビューは Opus（実装とは別のエージェント）、方針・設計の相談役は Fable、読むだけの調査は Sonnet、機械的な確認は Haiku
