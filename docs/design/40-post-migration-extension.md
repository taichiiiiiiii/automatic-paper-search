# 40. 移行後の拡張設計（P6）— 拡張の手順・認証・無料枠・独自ドメイン

状態: 設計案（2026-10-21）。実装は P5 切替（Tier C まで）の後。[39](39-typescript-cloudflare-migration.md) の P6 行を具体化する。個別機能（ログイン、マイリスト、通知、AI）は、着手時に各 1 本の設計書を足す。ここは**共通の土台と順序**だけを決める。

数値は 2026-10 時点の公式ドキュメントの記憶に基づく。**(verify)** は P6 着手前に公式ページで確認する。

## 1. 方針

1. **全部 Cloudflare の無料枠に収める。** 超えそうな機能は作らず、先に上限を見積もる（§5）。
2. **読み取りは静的、書き込みだけ Worker。** 公開データ（論文・テーマ・家系図）は今のまま静的配信。ログインが要る機能（マイリスト、通知設定）だけ `apps/api` を通す。
3. **同じ規約で足す。** 新機能は §2 の手順どおりに足し、既存の契約テスト（パス直書き禁止、CSP、no-skip）を通す。
4. **個人データは最小限。** 持つのはメール（ログイン用）とマイリストの論文 ID だけ。収集する前にプライバシー表記を書く（§3.4）。

## 2. 機能を足す手順（拡張のレール）

| 足すもの | 置き場所 | 規約 |
|---|---|---|
| 新しい API ルート | `apps/api/src/routes/<name>.ts` を Hono で書き、`app.ts` に 1 行登録 | 入力は zod（`packages/core/src/schemas`）で検証。origin・content-type・body サイズの検査は共通ミドルウェアを使う。secret を応答・ログに出さない |
| 新しい画面 | `apps/web/app/<route>/` | データはブラウザ側 fetch（ビルドに埋め込まない）。インラインスクリプトを増やさない（CSP 契約テスト） |
| 新しい収集・生成 | `apps/pipeline/src/<area>/` と workflow | 出力先は `@paperpilot/core/layout` のヘルパーだけ。パス文字列は書かない（`noPathLiterals` が落ちる） |
| 新しい共有型・形式 | `packages/core/src/schemas` | schema → 型の一方向。公開 JSON は形式のバージョンを持つ |
| 新しい永続データ | D1 のマイグレーション（`apps/api/migrations/NNNN_*.sql`） | 追加のみ。破壊的変更は 2 段（追加 → 移行 → 削除）。プレビューと本番で DB を分ける |
| 新しい secret・変数 | `wrangler.jsonc` の `vars`（非機密）／ Cloudflare の secret（機密） | 値はコミットしない。必要な変数は README の一覧に足す |

完了条件（どの機能でも）: テストはモック（外部 API を叩かない）、`no-skip-gate` 緑、プレビューで dry-run 動作、レビューで重大・中程度 0。

## 3. 認証とマイリスト

### 3.1 候補の比較

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. Better Auth ＋ D1（推奨）** | メール・マジックリンク、必要なら GitHub／Google の OAuth。セッションは D1 | TS で完結、Workers で動く、無料枠内 | メール送信手段が要る（§3.3） |
| B. Cloudflare Access | Cloudflare 側でログイン | 実装ほぼ不要 | 無料枠は 50 ユーザーまで。一般公開には不向き |
| C. 自前（パスワード） | — | — | 保管責任が重い。採らない |

推奨は A。個人利用（自分だけ）で足りるなら、B で先に始めて必要になったら A に移ってもよい。

### 3.2 構成

- Cookie は**同一サイトで張る**。API が別オリジン（`*.workers.dev`）だと第三者 Cookie 扱いになり壊れやすいので、**独自ドメインで `/api/*` を同一オリジンにする**（§6）。独自ドメインを使わない間は、ログイン機能を入れない。
- D1 のテーブル案: `users`、`sessions`、`saved_papers(user_id, paper_id, added_at)`、`notification_prefs`。論文 ID は公開データの安定 ID をそのまま使い、論文本体は D1 に複製しない。
- CSRF: `SameSite=Lax` ＋ 書き込みは JSON の POST のみ ＋ 既存の origin 検査。
- ログイン画面を含むページは、既存の CSP（全ページ同一）をそのまま通す。

### 3.3 メール送信（要決定）

マジックリンクにはメール送信が要る。無料で使える候補は Cloudflare Email Sending（提供状況 (verify)）、Resend の無料枠（3,000 通／月 (verify)）など。2026-10-05 に「メール／SMTP は移植しない」と決めているため、**通知用メールとは別の決定**として、ログイン機能に着手する時にユーザーへ確認する。OAuth（GitHub／Google）だけにすればメール送信は不要。

### 3.4 個人データの扱い

- 保管: メール（ハッシュ化は不要だが列は暗号化しない前提で最小限）、マイリストの論文 ID、通知設定。
- 削除: 「アカウント削除」で全行を消すボタンを最初から作る。
- ログ: メール・Cookie 値を Worker のログに出さない（契約テストで検査）。
- 公開ページにプライバシー表記を足してからログインを有効にする。

## 4. 通知と AI

### 4.1 通知

- 既存の Slack 通知（P4a で移植済み）は運営者向けのまま。**利用者向けの通知**（保存した論文の更新、新着のダイジェスト）は、メール送信が決まってから設計する。
- 先に作れるもの: ブラウザ内の「新着の差分表示」（最後に見た日時を localStorage に持つ。サーバー不要）。
- Cron Triggers（無料枠で利用可）で日次の集計を `apps/api` から回す案はあるが、収集は GitHub Actions のままにする（データ生成と配信を分ける）。

### 4.2 AI（要約・意味検索）

2026-10-05 に「Stage 3 embedding はやらない」と決めている。ここで足すのは**別の用途**。

| 機能 | 実装案 | 無料枠での扱い |
|---|---|---|
| 意味検索 | Workers AI の埋め込み ＋ Vectorize（有料のことがある (verify)）／ ビルド時に作った埋め込みをシャード JSON にしてブラウザ側で近傍検索 | 後者は無料。論文数 × 次元数でサイズを見積もってから決める |
| 要約 | ビルド時（GitHub Actions）に LLM で作り、静的 JSON として配信 | 実行時の LLM 呼び出しをなくせば枠の心配がない |
| 質問応答 | 実行時の LLM 呼び出しが必要 | Workers AI の無料枠 (verify) を超えるなら作らない |

原則: **LLM は実行時に呼ばず、ビルド時に作って静的配信**する。実行時に呼ぶ機能は、枠の見積もりとレート制限（既存の `QuotaCounter` を流用）が設計に入るまで作らない。

## 5. 無料枠の見積もり（P6 着手前に再確認）

| 資源 | 無料枠 (verify) | 今の使い方 | P6 で増える分 |
|---|---|---|---|
| Pages 静的配信 | 帯域は実質無制限、ビルド 500 回／月（Direct Upload は対象外） | 公開 JSON の配信 | 変化なし |
| Workers リクエスト | 10 万／日 | テーマ依頼のみ（少量） | ログイン、マイリストの読み書き |
| Durable Objects（SQLite） | 10 万リクエスト／日 (verify) | `QuotaCounter` | 変化なし（依頼上限のみ） |
| KV | 読み 10 万／日、書き 1,000／日 | テーマ manifest 等 | 使わない（書き込み枠が小さい） |
| D1 | 読み 500 万行／日、書き 10 万行／日、5 GB | 未使用 | users、sessions、saved_papers |

見積もりの考え方: 1 利用者が 1 日にマイリストを 20 回読み書きすると仮定すると、Workers の 10 万／日は**約 5,000 人日**で尽きる。個人〜小規模利用なら十分。超えそうな兆候（日次 5 万リクエスト）が出たら、アラートを出して機能を止める（`DISPATCH_MODE` と同様の明示スイッチ）。

## 6. 独自ドメイン（判断待ち 3 の整理）

| | 使わない（`*.pages.dev` ＋ `*.workers.dev`） | 使う |
|---|---|---|
| 費用 | 0 | 年 ¥1,500 前後 (verify) |
| API | 別オリジン。`connect-src` に API ホストが要り、CORS が要る | 同一オリジン `/api/*`。CORS 不要 |
| ログイン Cookie | 第三者 Cookie 扱いで不安定 | 同一サイトで安定 |
| URL の安定 | ホスト名が変わると外部リンクが切れる | ドメインを保てば、ホスティングを変えても URL が変わらない |

**推奨**: 切替（P5）の時点で独自ドメインを取る。URL を後から変えると、転送ページと sitemap・canonical をもう一度作ることになる。ログインを入れない間も、URL の安定のために価値がある。取らない場合は、ログイン機能は作らず、§4 のうち静的にできるものだけを足す。

## 7. Tier C（Python 削除）の後のリポジトリ

```
apps/web        Next 静的書き出し（画面）
apps/api        Hono Worker（API、D1、Durable Objects）
apps/pipeline   収集・生成・リリース（Node）
packages/core   共有の型・schema・layout
data/           published | state | inputs | config
legacy/         gh-pages-site（転送ページ。Tier C の後に整理）
```

開発ルール（CLAUDE.md／README）は、Tier C の commit で TS 版に書き直す: pnpm コマンド、テストの流れ、`no-skip-gate`、パス直書き禁止、外部 API は常にモック、secret は `.env` と Cloudflare／GitHub の secret のみ。Python 前提の記述（pytest、`paperpilot/`）はすべて消す。

## 8. 実施の順序

1. **P5 切替**（独自ドメインを同時に決める）。
2. **P6-0**: プライバシー表記、無料枠のアラート、D1 のマイグレーション基盤（プレビュー／本番を分ける）。
3. **P6-1**: ログイン（A 案）とマイリスト。
4. **P6-2**: 静的な AI 成果物（要約 JSON、近傍検索用の埋め込みシャード）。
5. **P6-3**: 利用者向け通知（メール手段の決定後）。

各段で「設計書 1 本 → 実装 → opus レビュー → 重大・中程度 0」を回す。

## 9. 判断待ち

1. **独自ドメインを取るか**（推奨: 取る。P5 と同時）。
2. **ログインの要否と範囲**（自分だけなら Cloudflare Access で足りる。一般公開するなら Better Auth）。
3. **メール送信の手段**（OAuth のみにすれば不要）。
4. **意味検索の方式**（ビルド時の埋め込みシャード推奨。サイズ見積もり後に確定）。
5. **利用者向け通知**を作るか。
