## 3. レビューの訂正 — 実データで再検算した結果

レビューの記述を事実として引用せず検算したところ、**CRITICAL 判定のうち 3 件が誤り**だった。

### 訂正① 「GitHub Pages で SPA ルーティングは不可能」は誤り

architect と code-architect が「存在しないパスは 404 になるので `/paper/<conf>/<id>/` は実現不可能、
ダミー HTML 28,300 個が唯一の解」と CRITICAL 判定した。

**`docs/404.html` は既に存在し（10,264 B）、そのソースコメント自身が機序を記録している:**

> `GitHub Pages serves this file for any unknown deep path but keeps that path in the URL bar.`

未知の深いパスは `404.html` にフォールバックし、URL は保持される — これが SPA フォールバックそのもの。
レビュー対象のリポジトリ内のコメントによって、レビューの CRITICAL が反証された。

**本物のトレードオフは残る**: HTTP ステータスは 404 のままで、現 `404.html` は
`<meta name="robots" content="noindex">` を持つ。∴ **クローラに拾わせたい URL には使えない。**
「不可能」ではなく「インデックスさせたい部分集合だけ静的生成する」という設計判断の問題。

### 訂正② 「学会横断には 50-70MB のダウンロードが必要」は誤り

**実測 `docs/*/papers.json` 合計 = 24MB**（2〜3 倍の過大主張）。
さらに検索インデックス（タイトル + arxiv_id + 学会のみ）を実際に生成して測ると:

| 索引の中身 | 件数 | raw | gzip |
|---|---:|---:|---:|
| title のみ | 28,300 | 2.26 MB | 0.70 MB |
| **title + 学会 + 論文 id**（採用） | **28,300** | **3.75 MB** | **1.11 MB** |

**学会横断検索は gzip 1.11MB で実装できる。** これは B 案の最大の弱点が安価に解消できることを意味し、
順位判断を動かした。初回ロードでは取得せず、検索ボックスへの最初の入力で遅延取得することで LCP を汚さない。

> **【2026-08-19 追記・自己訂正】** 当初この表に「2.69 MB / gzip 0.73 MB」と書いたが、これは
> `arxiv_id` を論文 id として測ったもので、**その `arxiv_id` は 28,300 行中 27,042 行（95.5%）が空**
> だった（下記③-2）。つまり**使える識別子を含まない索引を測っていた**。実際に使える id を入れると
> **3.75 MB / gzip 1.11 MB**。当初値は約 52% の過小である。

### 訂正③ C 案の前提「14 メジャートピック」は存在しない

C 案は `conferences.json` の `top_tags` を根拠にしたが、あれは**各会議の上位 6 件だけの打ち切り**であり、
設計されたタクソノミーではない。実データは **63 タグ**（`TOPIC_RULES` は 60 カテゴリ）。

| タグ | `conferences.json` 経由 | `papers.json` 実数 | 誤差 |
|---|---:|---:|---|
| Detection | 78 | **2,176** | **27.9 倍の過小** |
| Benchmark | 431 | 2,435 | 5.6 倍 |
| Agent | 443 | 2,252 | 5.1 倍 |

加えて **`Face` タグは 1,883 本中 最低 41.9% が英語の動詞 "face"（直面する）への誤爆**（#356）。

⇒ **どの案を採っても `conferences.json` の `top_tags` を件数表示に使ってはいけない。**
トピック件数は `papers.json` から集計する。

### 訂正③-2 `papers.json` には使える論文キーが無い（自己訂正・2026-08-19）

本書の初版は永続リンクを `?focus=<arxiv_id>` と書いていたが、**これは 95.5% の論文で機能しない**。

| | 論文数 | `arxiv_id` 空 |
|---|---:|---:|
| arXiv 由来（aaai-2026 / eccv-2024） | 1,258 | 0 |
| OpenReview 由来（iclr-2026 / icml-2025 / neurips-2025） | 13,894 | **全行** |
| ACL Anthology 由来（acl-2025 / emnlp-2025） | 3,508 | **全行** |
| CVF 由来（cvpr-2025 / cvpr-2026 / iccv-2025） | 9,640 | **全行** |
| **合計** | **28,300** | **27,042（95.5%）** |

一方 `arxiv_url` は **100% の行に存在**し、収集元 4 系統すべてが URL 中に安定 id を持つ。

| ホスト | 例 | 導出される id |
|---|---|---|
| `openreview.net` | `forum?id=rlZeILv3fm` | `rlZeILv3fm` |
| `arxiv.org` | `/abs/2403.06764v3` | `2403.06764`（版サフィックスを除去） |
| `aclanthology.org` | `/2025.acl-long.153/` | `2025.acl-long.153` |
| `openaccess.thecvf.com` | `/html/<stem>.html` | `<stem>` |

実データで **28,300 / 28,300 を抽出でき、失敗 0**。実装は `paperpilot/scripts/build_search_index.py`
（テスト 23 件、ブランチ `feat/355-search-index`）。

⇒ **永続リンクは `arxiv_id` ではなく、この導出 id を使う。**

  リポジトリ全体（`.py`/`.js`/`.html`）でも参照 0。B 案がこれを「今週のおすすめ」に使うのは誤り。
- **`LLM` タグが 28,300 本中 10,099 本（35.7%）** — C 案の面積比例グリッドは破綻する。
  （2026-08-20 訂正: 旧記載「28,310 本中 10,108 本」は分母に `docs/daily/papers.json` の
  10 本を含めていた。`daily` は会議ではなく、`build_pages.NON_CONFERENCE` が除外する死データ。

## 4. 決定

> ### **B 案（カタログが背骨）を base に、A 案の系譜前面化を接ぎ、横断検索インデックスを足す。C 案は不採用。**

### C 案を落とす理由

4 観点中 3 つで最下位圏（Borda 最下位）であることに加え、**独立に検算した前提が 2 つとも崩れた**（訂正③）。
背骨に据えるデータの品質が、背骨に必要な水準に達していない。
トピック軸そのものは有用なので、**フィルタ／ファセットとして B 案の中に取り込む**。

### A 案を単独では採らない理由

A 案はデザイン品質が最高（ui-reviewer の 10 項目中 **8** 達成。B 案 4、C 案 6）で、
PaperPilot の独自性そのものを背骨にする。**思想としては A 案が正しい。**

しかし**背骨に据えるデータが最も薄い**:

| 系譜データ | 実態 |
|---|---|
| 会議家系図 | **10 会議中 2 会議のみ**（`iclr-2026` 108KB / `eccv-2024` 38KB、残り 8 会議は ~290B の空スタブ） |
| テーマ家系図 | 3 本 |
| deep tree | 14 本 |

A 案の弱点を消すには 8 会議分の系譜生成が要る = LLM コストとパイプライン投資であって、
フロントエンドの再設計では解けない。**再設計をデータ生成の完了に人質に取ってはいけない。**

対して B 案の弱点（横断検索が無い・独自性が薄い）は、訂正②のとおり **gzip 1.11MB のインデックス**と
A 案の系譜前面化を接ぐことで**フロントだけで解消できる**。**直せるコストが逆**なのが決め手。

### 採用する形

確定前提「探す → 選ぶ → 系譜を辿る」の 1 本道への写像:

| 段 | 実装 | 根拠データ |
|---|---|---|
| **探す** | トップに検索ボックス 1 つ（`search-index.json`、gzip 1.11MB、10 学会横断、初回入力時に遅延取得）＋ 学会 10 カード。トピックはファセット | 28,300 本すべて |
| **選ぶ** | 学会カタログ（既存 URL 維持）でフィルタ → カード展開。論文詳細は**インライン展開**、永続リンクは `?focus=<論文 id>`（id は下記③-2 のとおり `arxiv_url` から導出する） | 既存 `papers.json` |
| **系譜を辿る** | カードから系譜へ。**データがある所だけ実グラフ**、無い会議は「未生成」と正直に出す | 2 会議 + 3 テーマ + 14 deep |

空スタブ 8 会議を系譜のように見せる現状（欠陥 #9 と同根）を、ここで断つ。

**A 案から接ぐもの**: 系譜の視覚言語（`--rel-*` 6 色）を**サイト全体の基調**にし、
カタログ側の白地カードと系譜側の暗いキャンバスという**視覚言語の分裂（欠陥 #8）を解消**する。
系譜を「別ページの機能」ではなく「カタログの各行が持つ属性」として扱う。

## 6. ホスティング — GitHub Pages のままとする

- Cloudflare Pages の唯一の実質的優位は **200 ステータスの SPA フォールバックと `_redirects`**。
  GitHub Pages の `404.html` フォールバックは動作するが **HTTP 404 + noindex** になる（訂正①）。
- **しかし本決定は SPA ルーティングを主導線に使わない。**
  学会カタログは実ディレクトリ、論文詳細はインライン展開（`?focus=`）。
- ⇒ **GitHub Pages のままでよい。**
  根拠は「移行コストが釣り合わない」ではなく、**「採用した設計が Cloudflare の優位点を必要としない」**。
- テーマ投稿 API の Cloudflare Worker はそのまま使う（現状どおり）。

## 9. フェーズ 2 の入力（着手前に必ず読むこと）

目的は §4「A 案から接ぐもの」＝**カタログと系譜の視覚言語の統一**。着手時点で確定している制約:

- 🔴 **`--rel-*` 6 色の hue は変更禁止。** `how-it-works` の `aria-label` が色名を明記しており
  （例「緑色の破線」）、3 ビューア + 凡例が同じトークンを共有する。
  **階層化は weight / dash / opacity で行う**こと。
- エッジ描画の単一真実源は `docs/assets/utils.js` の `PP.edgeStyle()`。分岐を増やすならここ 1 箇所。
- **系譜データは薄いまま**（会議家系図は 10 会議中 2 会議のみ、残り 8 会議は ~290 B の空スタブ）。
  §4 の「空スタブを系譜のように見せない」方針は据え置き。
- **タグ品質は未修正（Issue #356）。** `Face` タグは 1,883 本中 **≥41.9% が英語の動詞 "face" への誤爆**。
  トピックを主導線に出すなら **#356 が先**。
- `conferences.json` の `top_tags` は**各会議上位 6 件の打ち切り**。**件数表示に使わない**
  （Detection は 78 と出るが実数 2,176 ＝ 27.9 倍の過小）。集計は `papers.json` から行う。
